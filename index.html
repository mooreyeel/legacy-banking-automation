Operating legacy bank apps

Banks and credit unions run back-office software with no way in but the screen. This is a design for an AI system that drives that UI like a human would — moving real money reliably, cheaply, and auditably, and stopping to hand a live session to a person the instant it can't proceed safely.

The problem

No API. Just the screen the staff already use.

The only integration surface is the UI. So the agent calls a typed task — and behind it, our system signs in and works the screens like a person, one guarded step at a time.

# The agent never touches a screen. It calls a typed task and gets a typed answer.
transfer_funds(from_acct, to_acct, amount, intent_key)
   → { confirmation_number, posted_at }        # it worked
   → declined INSUFFICIENT_FUNDS              # a clean business "no"
   → escalation { work_item, live_session }   # a human is handling it

Every task returns the same envelope: a status, then exactly one of outputs, a typed decline, or an escalation. No UI words, no selectors, no stack traces — an agent developer can write complete handling code from the contract alone.

The five rules everything obeys

Safety by design, not by a permissions list.

These aren't guidelines bolted on top. They're structural — the dangerous moves are impossible to express in the system.

01

Fail = stop

A failed check halts with zero further actions. Never act on a page you haven't confirmed.

02

Fire once

An action never fires twice blindly. A re-clicked submit is a double transfer.

03

Two keys for money

Nothing irreversible fires without a ledger proof this intent hasn't run and an outside go-ahead.

04

No model at runtime

The model works offline, authoring under review. Runtime is deterministic replay.

05

Nothing raw stored

Checks verify live screen values; evidence is masked the moment it's written.

How it works · one loop, every step

Look → identify → locate → act → verify.

The executor never assumes it knows where it is. Every single step re-derives the world from a fresh look at the page, then verifies the act landed before moving on.

Read the render

Ask the browser what it drew (a DOM snapshot across frames), not the pixels.

On an API-less app, the readback is the only receipt you get.

“We verify the app accepted the value — not that we pressed the keys. A field you set is not a field the app took.”
Finding a field

§3Locator tiers — and drift as an early warning.

Each element carries an ordered list of ways to find it. A tier must match exactly one element or it fails to the next. We log which tier fired on every action.

tier 1Label. The input just right of or below the text "Amount." How a human navigates, and the most stable thing on a legacy screen.
tier 2Structure. Position relative to a nearby landmark, when there's no usable label.
tier 3Text pattern. For reading a value like $1,234.56.
tier 4Image. Last resort, on a pixel-only surface with no structure at all.

💡 The payoff

When tier 1 quietly starts failing over to tier 2 across runs, that's the earliest signal a screen changed — visible in the logs before a single user-facing failure. Drift detection falls out of the design for free.

The execution model

§2The money path is a guarded state machine.

Not a status field code could just set to "done." Guarded states make the dangerous transitions impossible to reach by accident — and provable in a test.

The one red arrow. The submit fires only on an outside go-ahead — a human, or a rule the institution set. There is no other path into TRIGGERING. On timeout the run stays prepared and never fires. There's no such thing as a filled-but-abandoned transfer floating around.

The intent ledger

One row per money-moving intent. The intent_key is the primary key — the database refuses to let two rows with the same intent exist.

CREATE TABLE intent_ledger (
  intent_key uuid PRIMARY KEY,  -- dedup lives here
  state text -- created|prepared|triggered|
             --   confirmed|aborted|unknown,
  receipt jsonb -- confirmation #, screen hash
);

Two keys, two questions

Idempotency-Key (header) guards the network — replays a lost-then-retried identical call.

intent_key (ledger) guards the money — it gates the UI click itself. A triggered intent is never re-submitted blind, even if the caller restarts and re-sends fresh. If two executors race, the DB lets exactly one win.

The scariest state

Never retry blind. Reconcile to a truthful, provable answer.

A triggered ledger row with no receipt is the unknown state — the click landed, but the confirmation timed out.

What we do

Run a read-only task — did_intent_post(intent_key) — that reads the account's recent activity before touching anything. It matches on a stamped reference in the memo where the app allows one; otherwise on amount + destination + time-window, escalating to a human on any ambiguity rather than guessing.

What actually kept the money safe

Not reconciliation — the ledger gating the UI submit. A triggered intent is never re-clicked. The bank has no idempotency key, so a blind retry would post twice; the ledger state is what prevents it. Reconciliation exists to give the caller a truthful answer and an auditor a provable one.

Where the LLM is — and isn't

§3The model is offline. Runtime is deterministic.

A model explores a new app offline, under human supervision, and proposes screen signatures and locator chains — which a human reviews. At runtime it's absent.

reliable

Replayable

Zero-judgment work should be deterministic. No improvisation on money.

cheap

~100× less

A vision call every step is far more cost and latency on UIs that barely change.

auditable

Reviewable

Improvised runtime behavior can't be reviewed or audited. Authored steps can.

The one narrow exception — a bounded, policy-checked, read-only recovery step — ships in shadow mode first. The halt stays the default.

Generalization & evidence

One base per vendor. A small overlay per institution.

~200 institutions run the same few vendor products. Write the base once; each institution gets a tiny overlay of local differences ("Member No." vs "Member Number").

The fork threshold: the moment an overlay needs if/else, it isn't config anymore — it becomes part of the program.

Evidence is a query, not a guess

Every run writes a structured trace — one event per line. For an auditor: who acted, under which task and version, approved by whom, for which member, with what result, and who fired the money step.

Early-warning signals

Locator-tier drift and a shift in the decline mix both show up before a member ever hits a failure. Observability isn't optional — the job that reads true state back is part of the system, monitored like anything else.
