Drive the UI when there is no API.

Back-office bank software often exposes no integration surface but the screen its staff already use. This executor operates that UI directly — check-then-act, one guarded step at a time — moving money reliably, cheaply, auditably, and freezing to hand a live session to a human the moment it can't proceed safely.

▶ Run it ↓ read the spec design.md ↗

The executor drives a mock legacy screen through three real runs. Step with Step or Space; it halts at each decision worth inspecting.

01

the contract

The agent never sees a screen. It calls a typed task and gets a typed answer — same envelope every time, no UI words, no selectors, no stack traces.

# the caller's entire surface area
transfer_funds(from_acct, to_acct, amount, intent_key)
    → { confirmation_number, posted_at }       # outputs  — it worked
    → declined INSUFFICIENT_FUNDS             # decline  — a clean business "no"
    → escalation { work_item, live_session }   # a human is handling it

# two keys, two questions
Idempotency-Key   # header — guards the network (lost-then-retried identical call)
intent_key        # ledger — guards the money (gates the UI click itself)
02

invariants the engine enforces

Not a permissions list — structure. The dangerous moves are impossible to express in the system.

  • 1A failed check halts with zero further actions. Never act on a page you haven't confirmed.
  • 2An action fires once. A re-clicked submit is a double transfer.
  • 3Nothing irreversible fires without a ledger proof this intent hasn't run and an outside go-ahead.
  • 4No model in the runtime loop. It authors offline under review; runtime is deterministic replay.
  • 5Nothing raw is stored. Checks verify live screen values; evidence is masked as it's written.
03

the money path is a guarded state machine

A status field could be set to "done." Guarded states make the dangerous transition unreachable by accident — and provable in a test.

fill+verify→
prepared

The one red arrow. prepared ⇒ triggering fires only on an outside go-ahead — a human, or an institution rule. There is no other path in. On timeout the run stays prepared and never fires; there is no filled-but-abandoned transfer.

intent_ledger

CREATE TABLE intent_ledger (
  intent_key uuid PRIMARY KEY,  -- dedup
  state text,  -- created|prepared|triggered
               -- |confirmed|aborted|unknown
  receipt jsonb -- conf#, screen hash
);

the scariest state: unknown

A triggered row with no receipt — clicked, but the confirmation timed out. Never retry blind (double-send); never abort (it may have worked).

Resolve with a read-only did_intent_post(intent_key) that reads the account before touching anything. The ledger already prevented the double-fire — reconciliation exists to give a truthful, provable answer.

verify

read it back — the only receipt an API-less app gives

locator tiers (drift = early warning)

tier 1 label      # input by its text — most stable
tier 2 structure  # position from a landmark
tier 3 text       # pattern e.g. $1,234.56
tier 4 image      # pixel-only last resort

tier 1 silently failing over to tier 2 across runs is the earliest sign a screen changed — before any user-facing break.

the model is offline

It proposes signatures + locator chains under human review, then is absent at runtime: doesn't look, doesn't pick targets, doesn't decide, never fires money.

reliable (deterministic replay) · cheap (~100× less than a vision call per step) · auditable (authored, reviewed). One bounded read-only fallback, shadow-first.
