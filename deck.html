Interface.ai · Design Round

Giving an agent hands
inside legacy bank UIs

A backend integration layer that operates back-office bank apps with no API — by driving the UI like a human. Reliably, cheaply, auditably.

Designed from a production computer-use system I built on a no-API portal
Say: "The agent decides what to do — this is how it reliably does it inside UI-only legacy apps. API is always preferred; this exists only for the long tail with none. I've built one of these in production, so I'll design from what held up and what broke."
The environment shapes everything

Three properties that drive every choice

  • Stable UIs, real runtime errors. Screens change slowly — but validation errors, "record not found," permission denials, dialogs, session expiry happen constantly. The happy path isn't useful.
  • Heterogeneous & legacy. Modern web, server-rendered framesets, or native desktop. No clean DOM, no test-IDs, no API. The only reliable surface is what a human operator sees.
  • Multi-tenant at scale. ~200 institutions × ~20 apps, many running the same vendor product branded differently. Automation must generalize or degrade gracefully — never be rebuilt per tenant.
Two anchor tasks throughout: get_balance (read-only) and transfer_funds (irreversible). The task's label drives unattended-vs-not, retry, evidence depth, and whether it must stop for approval.

The model is offline: it proposes screen signatures & locator chains under human review. At runtime it's absent — no picking targets, no deciding to proceed, never fires money.
Trade-off: deterministic replay + auditability + ~100× cheaper than a vision call every step, on UIs that barely change. The one bounded runtime fallback ships in shadow mode first.
The task contract

The agent never sees a screen

  • It calls a typed task from a catalog it discovers via GET /tasks?tenant= — inputs, safety label, whether it needs consent.
  • Every task returns the same envelope: a status + exactly one of →
outputsit worked
declinetyped business "no"
escalationa human has it
No UI words, selectors, screenshots, or stack traces ever cross this line. An agent-dev writes complete handling from the contract alone — without looking under the hood.
Trade-off: a typed catalog over "let the agent click buttons" — reviewable, auditable, and a business "no" (insufficient funds) is a branch, not an error.

  • Snapshot, don't screenshot-and-guess: ask the browser what it rendered (CDP DOMSnapshot) — a flat table of every visible element, text, geometry, across frames. Pixels only for evidence + last-resort OCR.
  • Wait on a condition, never a blind sleep — budgets (15s load / 5s in-screen / 20s post-submit); one retry, then hard stop. That's how you tell "slow" from "dead."
On an API-less app, readback is the only receipt you get. Type → read it back. Click → wait for the expected next screen. Verify the postcondition, not the keystroke.
Locating on a messy legacy screen

A tier ladder — and log which rung fired

1Label — the input just right of / below the text "Amount"most stable; how humans navigate
2Structural — position from a nearby landmarkframesets, nested tables
3Text pattern — read a value like $1,234.56no usable label
4Image match — pixel floor, read-onlyno structure at all
A tier must match exactly one element or it fails to the next. We log which tier fired every action — tier-1 quietly failing over to tier-2 across runs is the earliest warning a screen changed, visible before anything breaks.
War story: that failover signal is real — it caught screen drift for me before a single user-facing failure. Re-locate from a fresh snapshot right before acting, so a popup that slipped in makes the click miss or fail verify instead of acting on a changed page.
Execution model

Guards, not a status field

A status field lets code just set a run to "done." Guarded states make the dangerous transition unreachable by accident — and provable in a test. Money crosses PREPARED → TRIGGERING only on an outside go-ahead.
Idempotency

Two keys, two different questions

Idempotency-Key HTTP header
  • Guards the network: a dropped-and-retried request replays the stored response — nothing re-runs.
  • Catches the ordinary dropped connection / auto-retry.
intent_key in the ledger
  • Guards the money: the caller mints it once for "this particular transfer."
  • Before firing, the executor advances prepared→triggered in the DB — two racers, the DB lets exactly one win.
The header only catches an identical retry. If the caller's process restarts and re-sends as a fresh call, the header sees something new — but the intent_key still catches it, because the ledger remembers the intent no matter how the request arrives.
The scariest state · the auditor's question

"Did the money actually move?"

Clicked submit, never saw the confirmation. Don't retry blind (double-send). Don't abort blind (it may have worked). A triggered ledger row with no receipt is the unknown state — so resolve it with a read-only task, never a retry.

Retry is safe regardless — the intent_key prevents a double-fire. Reconciliation exists to give the caller a truthful answer and an auditor a provable one. Match on a stamped intent_key in the app's memo field where one exists; else (amount, to_acct, time-window) + human confirm on collision.
War story (your climax): "I hit exactly this — recorded a submit as complete without capturing the confirmation, and couldn't tell 'pending on the other side' from 'never landed.' That phantom-send is why reconciliation is a first-class read-only task, not an afterthought."

  • The work item is plain domain words: "expected the confirm screen, saw an 'account flagged' dialog" — masked inputs, everything already done (incl. anything irreversible), a live session URL.
  • Cede: human drives the same session; viewing ≠ control; control is an exclusive lock — never both acting at once. Every input recorded as theirs.
  • Resume: resume-at-step · complete-by-hand · abort. Each takeover becomes raw material for the next task version.
War story: an undeclared dialog escalated once → human resolved → shipped as a declared branch → now it returns cleanly. Each escalation makes the next less likely. Desktop that can't share a session degrades to assist-mode: we prepare + check the ledger, human clicks in their own session.
Safety & data

By design — not a permissions list

  • The catalog is the boundary. If a task isn't in it, the agent can't ask for it. Inside a task, only reviewed steps exist — there's no click() the caller can call.
  • Money stops at the confirmation screen. Fill everything, check the on-screen summary against typed inputs, ledger sits prepared, submit fires only on an outside go-ahead.
  • Secrets live in a vault, injected only at login — we record "typed password," not the password. MFA secret is a human step if the org wants.
  • Member data is never stored raw; evidence is masked at the moment it's written, so a screenshot can be redacted without weakening the check that already ran against the live value.
We start every institution under human review; only after enough clean supervised runs does it earn auto-run. A good success rate never bypasses this.
Evidence & observability

One trace, two readers

Debugger
  • A step-by-step timeline: at any freeze, expected vs. what showed up, which tier found each field, a masked shot at the boundary.
Auditor
  • An investigation becomes a query: who acted (our identity + any human takeover), under which task+version, approved by whom, for which member, with what result, and who fired the money step.
Two early-warning signals, both visible before a member hits a failure: locator-tier drift (tier-1→tier-2), and a shift in the decline mix per task/version/institution.

  • 'Member No.' vs 'Member Number' is config. The moment an overlay needs if/else, it's not config — you fork. That rule keeps 200 tenants from becoming 200 codebases.
  • Everything is pinned to a version; fixes roll in waves to partners first; a stale task suspends itself rather than improvising.
  • Onboarding = discovery agent maps their apps to a known vendor/version → inherit the base → generate the overlay via supervised read-only runs → their staff signs off. Not a project.
The design I'd stand behind

Small, coherent, opinionated

  • Typed task contract — the agent never touches a screen; a business "no" is a branch.
  • One drive-UI loop — snapshot → identify → locate (tiers) → act → verify. Readback is the receipt.
  • Guarded state machine + intent ledger — the dangerous transition is unreachable by accident, and reconciliation answers "did it move?"
  • Escalation as a state — pause, cede, resume; every takeover trains the next version.
  • Safety by design — catalog, reviewed steps, stop-at-confirm, vault, masked evidence.
  • Base + overlay, fork when it needs logic — generalizes across surfaces and tenants without per-tenant rebuilds.
Extensions it grows into cleanly: a completed task emits a runnable Playwright test (the screen model already is a page-object); draft→approved confidence gating; a single bounded, policy-checked assisted fallback, shadow-first.
Close: "That's the design. It's deliberately small — I'd rather defend a coherent core than survey options. Where do you want to push?"
